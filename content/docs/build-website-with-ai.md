这篇教程把散落各处的材料重新拼成一条主线：**让 AI 写出代码 → 在本机跑起来 → 免费托管发布 → 拿到一个可分享的链接**。这条主线共四步——**装客户端 → 配 API Key → 把 Agent 用明白 → 写并发布**；中间插入前后端与数据库概念，不是让你学编程，而是让你在 AI 写错时能看出错在哪一层；「把 Agent 用明白」那一章讲三件事：它为什么能自己干活、怎么用规范把需求说清、怎么立一份它能听懂的规矩；最后一章的发布，直接交给 Agent 自动化。

先说立场：AI 编程降低的是**入门门槛**，不是取消理解成本——准确地说，它不是「不需要懂任何技术」，而是把学习从「先学后用」变成「边用边学」。全文不承诺「几天成为工程师」，只承诺走通后你会多一个能自己改的网站。

## 一、路线总览

四步各自的要点：

1. **装客户端**：给自己配一个「AI 助手」。它要有眼睛（读项目文件）、有手（改文件、敲命令）、有脑子（大模型）。
2. **配 Key**：接通模型服务的付费通道。Key 就是通行证，填错一步它就说不出话。国内环境推荐「第三方中转 + CC-Switch / NewMax」，不用科学上网（见 3.1）。
3. **把 Agent 用明白**：搞清它为什么能自己干活、怎么用规范把需求说清、怎么立一份它听得懂的规矩。
4. **写并发布**：用自然语言描述你要什么，AI 生成项目；跑通后，发布这一步交给 Agent 自动化。

关键认知来自 **Vibe Coding**（Andrej Karpathy 于 2025 年初提出），四条原则可直接当口诀：意图优先、快速迭代、信任但验证、上下文经营。

一个必须接受的前提：**AI 会写错代码**。这被称为「幻觉」——模型按概率生成内容，大多数时候准，偶尔会一本正经地编出不存在的函数。所以后面每一节都带着「怎么验证」这一问。

## 二、装一个 Agent 客户端

### 2.1 三种形态怎么选

以 Codex 为例（界面与版本会变，以官方页面为准）：


| 安装方式       | 适合人群            | 安装难度 | 新手推荐度  |
| ---------- | --------------- | ---- | ------ |
| 桌面应用       | 喜欢图形界面，希望直接上手   | 低    | 推荐新手首选 |
| VS Code 插件 | 长期用 VS Code 写代码 | 中    | 次选     |
| CLI 命令行    | 熟悉终端工作流         | 中    | 熟悉终端再选 |


选择原则很朴素：**你平时在哪写东西，就用那个形态**——不写代码用桌面应用，装了 VS Code 的装插件，只玩命令行的选 CLI。三者可共用同一套配置，不必维护三份。

如果连「选形态」都嫌麻烦，可以直接用桌面客户端——见 2.4 里的 NewMax。

### 2.2 装之前先补运行环境

CLI 形态对系统有要求（同上表）：


| 系统      | 版本要求                                 | CLI 额外要求                          |
| ------- | ------------------------------------ | --------------------------------- |
| Windows | Windows 10/11；桌面端需 Windows 10 19041+ | Node.js 22+、npm 10+、Git Bash、网络连接 |
| macOS   | macOS 12 或更高                         | Node.js 22+、npm 10+、网络连接          |
| Linux   | Ubuntu 20.04+、Debian 10+、CentOS 7+ 等 | Node.js 22+、npm 10+、网络连接          |


每个系统选一条对应的路装好即可。**装完记得重开一次终端**，新命令才会生效。

**Windows**（二选一）：

方式一，用系统自带的 winget（Windows 11 与 Win10 1809+ 已内置）：

```powershell
winget install OpenJS.NodeJS.LTS
```

方式二，到 [Node.js 官网](https://nodejs.org/en/download) 下载 Windows 安装包（`.msi`）双击安装——对新手最不容易出错，安装选项保持默认即可。

**macOS**（二选一）：

方式一，用 Homebrew（需先装好 Homebrew）：

```bash
brew install node
```

方式二，到 [Node.js 官网](https://nodejs.org/en/download) 下载 macOS 安装包（`.pkg`）双击安装。

**Linux**：

```bash
# Ubuntu / Debian
sudo apt update
curl -fsSL https://deb.nodesource.com/setup_lts.x | sudo -E bash -
sudo apt-get install -y nodejs

# CentOS / RHEL / Fedora
sudo dnf install nodejs npm
```

### 2.3 装客户端本体

不想碰命令行的，可以直接用桌面客户端（见 2.4 的 **NewMax**）；如果你走命令行，方式如下（请以官方最新文档为准）：

```bash
# Codex CLI
npm install -g @openai/codex

# Claude Code
npm install -g @anthropic-ai/claude-code
```

装完必须验证，能看到版本号才算成功：

```bash
codex --version
claude --version
```

![安装完成后用 --version 确认客户端可用](/images/docs/build-website-with-ai/build-verify-install.jpg)

国内网络卡在下载上时，一个临时办法是先切 npm 镜像（Windows / macOS / Linux 通用）：

```bash
npm config set registry https://registry.npmmirror.com
```

> **Windows 用户注意**：上面的 `npm` 命令建议在 **Git Bash**（装 Git for Windows 时一起装上）里执行，兼容性最好。若在 PowerShell 里报「无法加载文件 …npm.ps1，因为在此系统上禁止运行脚本」，那是执行策略限制，不是装错了——改用 Git Bash，或先以管理员身份运行一次 `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`，然后重开终端。
>
> 另外：Claude Code 对 Windows 的支持方式会随版本变化，若官方文档提示走 WSL，就在 WSL 的 Linux 终端里安装。

### 2.4 NewMax：桌面客户端

前面三种形态（桌面应用 / VS Code 插件 / CLI）都围绕「写代码」。如果你压根不想打开终端，可以直接用一个桌面客户端 **[NewMax](https://newmax.cc)**（[下载页](https://newmax.cc/download)），支持 macOS / Windows / Linux。

它的定位是「**本地优先的 AI Agent 客户端**」：每个工作区绑定一个本地文件夹，读取你的文件、调用工具、编排多步任务，尽量把数据留在你自己的电脑里。几个值得关注的点：


| 能力             | 说明                                                                                         |
| -------------- | ------------------------------------------------------------------------------------------ |
| 多模型接入          | 可接 Claude、OpenAI、DeepSeek、Kimi、Qwen、智谱、Ollama 等一批提供商，另有本地模型服务；按「提供商 → 模型」二级菜单切换，每个对话各记各的模型 |
| Key 存在本机       | API Key 保存在本地，敏感资料不必上传云端                                                                   |
| Skill 与 MCP 扩展 | 内置 Skill 系统，支持连接 MCP 工具，把固定流程沉淀成可复用能力                                                      |
| 数据留本机          | 工作区文件与记录存在本地，可自动备份，也可一键清空本机数据                                                              |
| 额外能力           | 全局快捷唤起、本地语音输入、定时任务、内置终端、联网搜索、对话导出                                                          |


个人版免费；团队管理、统一配置、私有化部署等能力按需升级企业版。

**该选 Codex 还是 NewMax？** 绕不开的现实差别是网络：Codex 是海外工具，官网订阅和官方 API 都要**科学上网**才能用；NewMax 是国内的本地 Agent 客户端，日常开发最常用的那几件事——读项目文件、改代码、跑命令、编排多步任务——它基本都有，而且**不需要科学上网**。


| 对比项  | Codex / Claude Code（海外客户端） | NewMax（本地桌面客户端）           |
| ---- | -------------------------- | ------------------------- |
| 网络   | 官网订阅、官方 API 需科学上网          | 国内网络直连可用                  |
| 上手   | 命令行或插件，要先补 Node 环境         | 图形界面，装上就能用                |
| 核心能力 | 读文件、改代码、跑命令、多步任务           | 同类核心能力，另有 Skill / MCP 扩展  |
| 配置   | 自己管 Key 与环境变量              | 设置里填 Base URL + Key，测通即激活 |
| 费用   | 官方订阅按美元计费，需境外支付方式          | 客户端个人版免费，模型费用按所选渠道付       |


两者不冲突，很多人是搭配着用：**能解决网络问题、想要最新能力，就用 Codex / Claude Code；想在国内网络下开箱即用、少折腾配置，就用 NewMax。**

**方式一：手动添加供应商**

1. 打开 NewMax，点左侧栏的「**设置**」。
2. 进「**模型**」，点右侧的「**自定义供应商**」。
3. 填 **API Base URL**。
4. 选 **API 格式**：服务商兼容 OpenAI 接口就选「OpenAI 格式」，Claude 原生接口选「Anthropic 格式」。
5. 填 **API 密钥**：把控制台里创建的那把 Key 粘进去（Key 通常只在创建时完整显示一次，记得存好）。
6. 点「**+ 添加模型**」手填模型 ID，或点「**从服务商拉取模型列表**」自动拉取。
7. 点「**测试连接并激活**」——测通才算配好。
8. 回到对话，在**输入框右侧的模型选择器**里按「提供商 → 模型」选中它。

![NewMax 设置 → 模型：选「自定义供应商」](/images/docs/build-website-with-ai/build-newmax-models.png)

![自定义供应商表单：填 Base URL、API 格式与密钥](/images/docs/build-website-with-ai/build-newmax-provider.png)

> 「使用 Responses API」这个开关，只有服务商确实支持 `/v1/responses` 端点时才打开；勾了但服务商不支持，请求会直接 404。

## 三、配好 API Key

这一步**最容易翻车**。因为「客户端」和「模型服务」是两回事：客户端只是外壳，真正的智力来自你 Key 指向的那个服务商。

### 3.1 选渠道：官方订阅还是第三方中转

在填任何配置之前，先决定 Key 从哪来。两条路：


| 对比项 | 官方订阅（OpenAI / Anthropic） | 第三方中转 + CC-Switch / NewMax |
| --- | ------------------------ | -------------------------- |
| 网络  | 需要科学上网                   | 国内直连                       |
| 支付  | 境外银行卡或虚拟卡，按美元付           | 人民币，一般扫码即可                 |
| 价格  | 官方定价                     | 按量计费，通常更便宜                 |
| 稳定性 | 官方一手，最稳                  | 取决于中转商，选口碑好的               |
| 配置  | 官网登录后客户端直接可用             | 填 Base URL + Key（见 3.2）    |


**如果你打算用官方订阅、但不懂怎么付款**，可以在群里联系群主帮忙代充值，比自己摸索快得多。想自己动手的，网络和付款分两步解决：

**① 网络问题**（只有走官方订阅才需要）

- 机场：[congyu](https://congyu.moe)
- 代理客户端（Clash 系）：[clash-verge-rev 下载页](https://github.com/clash-verge-rev/clash-verge-rev/releases)

**② 付款问题**（下面两个是公开视频教程，仅供参考）

- 低价订阅：[菲律宾区低价订阅思路](https://youtu.be/ShsfLVdoDNo)
- 国内银行卡订阅：[不用代充、不买虚拟卡，用国内银行卡订上](https://youtu.be/o9GhNogsFuI)

> 这两条路只说明「有人这么走通了」，不代表适合所有人：跨区订阅等操作存在**掉订阅甚至封号**的可能，建议先用小额试。教程仅供参考，如果你有更稳的方法，欢迎联系我们，我们随时更新这份文档。

**结论（推荐用法）**：对国内大多数人来说，**第三方中转 + CC-Switch / NewMax** 是最省事的一条路——不用科学上网、不用境外卡，把自定义厂商指向一个中转服务（推荐：[sshzyu](https://sshzyu.com)），填好 Base URL 和 Key 就能用。下面 3.2 讲这套配置怎么落地。

### 3.2 用 CC-Switch 管理配置

配置本身不复杂，麻烦的是「今天用官方、明天切中转」这种多套 Key 的场景。CC-Switch 这类工具的价值是「集中管理 + 一键切换」，把多组 Key 存在一处，用哪套切哪套。如果你用的是 NewMax 这类桌面客户端，直接在设置里切换模型即可（配置见 2.4）

1. 打开 CC-Switch → 进入 Codex → 点「+」新增配置
2. 选择供应商，列表里没有就选「自定义」
3. 填 `API Key` 和 `Base URL / Endpoint`（以你的服务商文档为准）
4. 保存，切换到该配置

![CC-Switch 中选择供应商](/images/docs/build-website-with-ai/build-ccswitch-provider.png)

![填写 API Key 与 Base URL / Endpoint](/images/docs/build-website-with-ai/build-ccswitch-config.png)

![保存后切换到该配置](/images/docs/build-website-with-ai/build-ccswitch-switch.png)

⚠️ **最容易翻车的顺序问题**：切换配置**必须在启动客户端之前**。已经在会话里再切是切不动的——环境变量在进程启动时就读进内存了。正确顺序：选定配置 → 重启终端 → 再运行。安全提醒：API Key 属于敏感信息，不要截图公开、不要发群、不要上传到公开仓库。

### 3.3 怎么确认配成功了

1. 启动客户端（CLI 是 `cd` 到项目目录再运行 `codex` 或 `claude`）
2. 输入 `/status`，看当前 Base URL 和模型对不对
3. 发一条测试消息（如「你好，你是什么模型」），能正常回复就算通了

![用 /status 确认 Base URL 与模型](/images/docs/build-website-with-ai/build-verify-status.jpg)

**排查顺序**：失败时**不要先怀疑模型**，按「Key 是否有效 → Base URL 是否写对 → 网络是否可达」三件套查。Base URL 多一个斜杠、少一段版本路径，都会直接失败。


| 常见错误                       | 重点检查                     |
| -------------------------- | ------------------------ |
| `401` / `Invalid API Key`  | Key 是否复制完整、密钥分组是否正确      |
| 配置文件没生效                    | 路径对不对、配置是否在文件最上方、有没有重启应用 |
| `codex: command not found`（macOS / Linux）／`'codex' 不是内部或外部命令`（Windows） | 重新打开终端；仍无效就重装 |


## 四、把 Agent 用明白

### 4.1 Claude Code 为什么能"自己干活"

#### LLM Loop：它是 Agent，不是聊天框

对话式 AI（ChatGPT / Claude.ai）的工作方式是：你问一句，它答一句，结束；不满意就再问一次，主动权始终在你手里。Claude Code 不是这样——你下达一个目标，它自己拆解步骤、自己调用工具、看结果、决定下一步，一直循环到任务完成。这个"思考—行动—观察—再思考"的循环就叫 **LLM Loop**。

由此带来三个结果：你可以给它一个模糊的高层目标（比如"帮我做一个番茄钟"），它会自己推进；执行中它会自我纠错（命令报错就读错误、调方案再试）；它不一定每一步都问你。所以**在让它"撒丫子跑"之前，要把上下文给好**（CLAUDE.md、Skills、计划等）。一个关键认知：底层大模型其实可以替换——这也是能用 DeepSeek、千问、GLM 等模型驱动它的原因；真正让它强于普通对话式 AI 的，是这套 Loop 机制加上 Harness 工程。

#### Agentic Search：它如何"读懂"你的代码库

很多人以为它像其他工具那样，先把项目代码上传到服务器建立索引。实际上**它不需要任何预先的代码库索引**——官方把这套机制叫 **Agentic Search**，工作方式和一个人类工程师冷启动项目完全一样：现场读文件、grep、追引用。


| 维度      | 传统 RAG 检索              | Claude Code 的 Agentic Search |
| ------- | ---------------------- | ---------------------------- |
| 工作方式    | 预先嵌入整个代码库为向量，查询时按相似度拼凑 | 现场读文件、grep、追引用               |
| 需要服务器索引 | 需要，且需持续维护              | 不需要                          |
| 代码变动处理  | 索引过期，可能返回已删除或重命名的代码    | 始终读取实时代码                     |
| 适合场景    | 老项目、不变代码库              | 活跃开发中的项目、大型 monorepo         |


它天生适合活跃代码库，不依赖可能过期的预建索引。但要注意：被读取进上下文的文件内容仍会发送给模型服务，处理敏感代码时依然要遵守公司安全规范。

#### Harness：脚手架比模型更重要

值得注意的是，决定表现的，不只是背后的模型，还有围绕模型搭建的"脚手架"——**模型能力决定下限，项目上下文、工具权限、规则文件和工作流决定上限**。可以把它抽象成 **7 个扩展点**，按"从底到顶"理解：先打好上下文和规则基础，再接入更复杂的外部工具。


| 层   | 组件                 | 作用                            | 加载时机     |
| --- | ------------------ | ----------------------------- | -------- |
| ①   | **CLAUDE.md**      | 项目上下文文件（背景、约定、禁区）             | 每次会话自动加载 |
| ②   | **Hooks**          | 会话生命周期钩子（启动/结束/文件写入等事件）       | 事件触发     |
| ③   | **Skills**         | 可复用的任务方法论（如"代码审查""部署"）        | 按需加载     |
| ④   | **Plugins**        | 打包一整套 Skills + Hooks + MCP 配置 | 装上后始终生效  |
| ⑤   | **LSP**（语言服务器）     | 给 AI 装上"跳到定义/查找引用"等 IDE 级导航   | 始终生效     |
| ⑥   | **MCP 服务器**        | 打通与外部工具（数据库、文档、票务系统）          | 始终生效     |
| ⑦   | **Subagents**（子代理） | 独立上下文窗口的实例，只返回结论              | 任务发出时创建  |


> 顺序很重要：不要在基础没搭好时就急着上 MCP 或 Subagents。先把 CLAUDE.md、Hooks、Skills 这三层基本功做扎实。

### 4.2 SDD：规范驱动开发

如果你只告诉 AI"帮我做一个网站"，它很可能做出一个和你期望完全不同的东西——模糊需求必然导致不准确的结果。**规范就是你和 AI 之间的"合同"**，写清三件事：要做什么（功能需求）、怎么做（技术方案）、做到什么程度（质量标准）。初学者不用一开始就写完美文档，从简单的 PRD 开始，项目复杂后再完善。

**PRD（要做什么）**。用户故事格式是"作为一个 [角色]，我希望 [功能]，以便 [价值]"，例如"作为一个博客读者，我希望能按标签筛选文章，以便快速找到感兴趣的内容"；验收标准格式是"When（操作）→ Then（预期结果）"，例如"用户点击 Python 标签 → 页面只显示标记了 Python 的文章"。也可以直接让 AI 把模糊想法变成结构化需求。

**SPEC（怎么做）**。一份完整的技术规范包含系统架构、技术选型、数据模型（有哪些表、哪些字段）、API 接口（URL、请求参数、返回格式）、目录结构。可以让 AI 从 PRD 自动生成 SPEC：把 PRD 贴进去，要求它推荐技术选型并说明理由、设计数据模型、列出所有 API、给出目录结构。

**质量规范（做到什么程度算合格）**：编码规范（风格、命名、注释）、测试规范（覆盖哪些场景）、安全规范（输入验证、认证授权、数据保护）。

**规范文件的组织**：建议在项目根目录建一个 `specs/` 文件夹统一管理：

```
my-project/
├── specs/
│   ├── PRD.md           # 产品需求文档
│   ├── SPEC.md          # 技术规范
│   ├── ARCHITECTURE.md  # 架构设计
│   └── API.md           # API 接口文档
├── src/                 # 源代码
├── CLAUDE.md            # 给 Claude Code 的项目说明
└── package.json
```

规范文件最大的价值之一，是**可以直接作为 AI 的上下文输入**——把 SPEC.md 提供给 Claude Code，它就能按你的技术方案精准写代码。

### 4.3 立规矩：CLAUDE.md

在项目根目录创建 `CLAUDE.md`，它是 Claude Code 的"项目说明书"，每次启动都会读取——写得好不好，直接决定它听不听话。示例：

```markdown
# 项目说明
这是一个 Next.js 14 + TypeScript 的电商后台管理系统。

# 代码规范
- 使用 TypeScript strict mode
- 组件用 PascalCase 命名
- API 路由放在 src/app/api/ 下

# 常用命令
- 启动开发：pnpm dev
- 跑测试：pnpm test
- 类型检查：pnpm typecheck

# 注意事项
- 不要修改 src/legacy/ 下的代码
- 数据库 migration 必须通过 drizzle-kit 生成
```

几条硬规矩：控制在 **200 行以内**（太长时 AI 会忽略靠后内容，大项目拆到 `.claude/rules/`）；用"跑测试"测试法验证——任何人说一句"跑测试"就能成功，说明写够了；权限控制写进 `settings.json`，比在 CLAUDE.md 里写"不要"更可靠；关键规则用 `<important>` 标签包裹，模型会更重视；分层写——根目录放全局规则，子目录放模块规则；大项目用 `.claude/rules/` 按 globs 匹配文件类型条件加载。

## 五、前端、后端与交互

你不需要会写代码，但需要知道「用户看到的那一层」和「数据存放的那一层」是分开的。这样 AI 出问题时，你能描述清现象。

### 前端：用户看到的那一层

前端是用户**直接看到和交互**的部分——排版、颜色、布局、动效，以及点击按钮、填写表单。三种语言的分工其实很直白：**HTML** 是结构（骨架）、**CSS** 是样式（皮肤）、**JavaScript** 是交互逻辑（大脑）。前端运行在**浏览器**里，处理轻量交互，把复杂请求交给后端。

### 后端：数据与逻辑

后端负责**数据处理、业务逻辑、数据库交互和安全控制**，工作分三层：接收请求 → 处理逻辑 → 管理数据。常见语言有 Python、Java、Node.js、Go；数据库分关系型（MySQL、PostgreSQL）和非关系型（MongoDB、Redis）。一个必须澄清的误解：**「与数据库交互」很重要，但不是后端的唯一任务**，它还要负责安全验证、业务规则、接口规范和性能优化。

### 它们怎么交互

两者通过 HTTP 请求 + JSON 数据 + API 接口。API 是前后端之间的「合同」，前端只要知道「接口叫什么、要传什么、会返回什么」，两边就能独立开发——这叫**前后端分离**。一次登录的流程是：用户输入账号密码点登录 → 前端调用 `POST https://example.com/api/login` → 后端验证并查询数据库 → 返回结果（登录成功 + Token）→ 前端显示欢迎页。后端对数据库的操作统称 **CRUD**：新增、读取、更新、删除。

```json
// 前端发给后端
{ "username": "holly", "password": "123456" }

// 后端返回
{ "status": "success", "token": "abc123xyz" }
```

三组容易被忽略的差异：**并发**上，前端每位用户各有副本、基本不存在并发问题，后端却要同时处理成千上万个请求；**缓存**上，前端缓存在浏览器，后端缓存在服务器或 CDN；**安全**上，前端侧重输入验证和身份验证流程，后端更全面（加密传输、访问控制、数据库保护），**核心安全实践在后端**——在给网站接上用户系统之前，这点值得先想清楚。

### 数据库结构设计

前面说后端"管理数据"，具体管的就是数据库。数据库结构设计，说白了是回答一个问题：**系统里要保存哪些数据，这些数据之间是什么关系？** 它由三部分组成——**表**（保存某一类实体，如用户表、订单表）、**字段**（表内的具体属性，如用户名、邮箱）、**关系**（表与表之间的关联）。设计时有一个关键原则：**从业务出发，而不是从数据出发**——先理解业务（注册、下单、支付、评论），再抽象出实体（用户、商品、订单），然后为每个实体建表，最后确定表之间的关系。

**三种常见的表关系**（关系型数据库如 MySQL、PostgreSQL）：

- **一对一**：A 表一条记录只对应 B 表一条。例如用户表与用户资料表——把数据拆开、减少冗余，敏感信息可单独存放。
- **一对多**：A 表一条记录对应 B 表多条。例如用户与订单——一个用户可有多个订单，一个订单只属于一个用户。**这是最常见的关系类型。**
- **多对多**：两边都一对多。例如学生与课程——需要通过**中间表**（关联表）实现，如 `student_course(student_id, course_id)`。

**电商系统怎么建模**：核心业务是注册登录、浏览商品、下单。可抽象出用户（User）、商品（Product）、订单（Order）、订单项（OrderItem）四张表，关系是：

```
User (1) —— (N) Order (1) —— (N) OrderItem (N) —— (1) Product
```

含义是：一个用户可有多个订单；一个订单可包含多个商品；一个商品也可出现在多个订单中。设计好关系后，后端业务就建立在这些表之上——注册是往 user 表新增记录，下单是新建 order + order_item，查看订单是通过外键关联查询，修改库存是更新 product 表。

**主键、外键与约束**（让数据库自己"懂业务"）：


| 约束类型            | 作用       | 示例                      |
| --------------- | -------- | ----------------------- |
| 主键（Primary Key） | 唯一标识一条记录 | user.id                 |
| 外键（Foreign Key） | 建立表之间的关系 | order.user_id → user.id |
| 唯一约束（Unique）    | 防止重复数据   | email 唯一                |
| 非空约束（NOT NULL）  | 确保必须有值   | username 不可为空           |
| 索引（Index）       | 提高查询性能   | 在 email 上建索引            |


这些约束的价值在于：后端不用每次手动检查，数据库本身就能挡住逻辑错误。此外还要考虑性能优化（索引、缓存、读写分离）、扩展性（字段预留）、安全性（密码加密、权限控制）、事务一致性（一组操作要么全成功要么全失败，如转账），以及数据冗余与规范化之间的平衡。

**数据库驱动与 ORM**：后端与数据库的通信靠"驱动"或 ORM。**数据库驱动**是后端语言与数据库之间的"翻译器"——例如 Python 要跟 MySQL 对话，需要一个 MySQL 驱动（如 `pymysql`），由它把 Python 命令翻译成 SQL。**ORM**（对象关系映射）是更高层封装，让你像操作对象一样操作数据库——它会自动生成 SQL、管理连接、把表映射成代码里的类。常见 Python ORM 有 SQLAlchemy、Tortoise ORM、SQLModel。简单理解：ORM 就像一个"数据翻译员"，让后端不用手写复杂 SQL 也能高效管理数据。

## 六、实战：做一个带动画的视觉站

这一节来自一篇广为流传的实战复盘。**先做声明**：其中「价值 1 万美元」「中介收费 5000 美元」「我只花了 2 小时」都是**个人说法**，本文不当作事实结论。可复用的是**方法**，不是数字。

**第一步，装两个设计技能。** 一个观察是：默认状态下 AI 的设计输出很平庸——同样的字体、同样的布局、同样的扁平感。实际做法是装两个插件：一个**前端设计技能**（据称由 Anthropic 构建，屏蔽 Inter 这类被过度使用的字体），一个 **UI/UX Pro Max**（据称提供 57 种界面风格、95 种调色板、56 种字体配对）。还建议把模式切到**自动模式**，让 AI 不必每步都请求许可——⚠️ 但请自己权衡：自动模式减少打断，也意味着你的干预变少。

**上面复盘用的插件，今天有更成体系的现成 Skill 可以替代。** 下面两个正好补上 AI 默认缺失的「设计」与「动效」能力（注意：它们与复盘当时用的具体插件并非同一批，是同类的替代选择）：


| Skill          | 它解决什么                                                                                 | 官网 / 仓库                                         |
| -------------- | ------------------------------------------------------------------------------------- | ----------------------------------------------- |
| **impeccable** | 给 Agent 补上「设计语汇」：从零构建界面、改造现有界面、并守住一套设计系统；内置对「AI 味」（AI slop，如侧边色条、每节都挂小标题、卡片套卡片）的识别与修正 | [官网](https://impeccable.style/)                 |
| **motion-web** | 专攻动效——主张「动效即材质」，用真实物理（弹簧阻尼）做高手感交互动画，内置 7 个可运行案例 + 自动化 headless 校验，防「假动画」              | [仓库](https://github.com/feitangyuan/motion-web) |


- **impeccable** 官网给自己的定位是「*The missing design vocabulary for agents*」——把 AI slop 变成你愿意交付的界面。它不只负责生成，还负责**审计**（对比度、排版、视觉层级、动效、无障碍）与**沉淀**（把规范写进 `DESIGN.md` / `PRODUCT.md`，让后续每次改动都守同一套规则）。支持 Codex CLI、Claude Code、Cursor、Gemini CLI 等多种环境，安装方式见官网。
- **motion-web** 是一个 Claude Agent Skill，主张「动效即材质」，覆盖 Three.js / Canvas 2D / WebGL / CSS 动效。装法照录仓库说明：

```bash
# macOS / Linux，以及 Windows 的 Git Bash
git clone https://github.com/feitangyuan/motion-web.git ~/.claude/skills/motion-web
```

Windows 的 **PowerShell** 里 `~` 不一定被正确展开，换成显式路径更稳：

```powershell
git clone https://github.com/feitangyuan/motion-web.git "$env:USERPROFILE\.claude\skills\motion-web"
```

（CMD 里对应写成 `%USERPROFILE%\.claude\skills\motion-web`。目标目录不存在时 git 一般会自动创建；若报错，先手动建好 `.claude\skills` 这一层。）

**第二步，找参考，不要凭空描述。** 实践中用 Awwwards 上一个站点作主要参考，但不是整页截图丢过去，而是**一部分一部分地截取**——首屏、首屏下方区域、页脚、单个项目页、加载屏幕。核心原则：**不要完全复制一个网站，从每个网站借用有效的东西**。参考里没有的部分（如作品列表页），另找类似风格的不同布局单独截图。

![把参考网站分区截取后喂给 AI](/images/docs/build-website-with-ai/build-reference-shots.jpg)

**第三步，写构建提示词。** 构建提示词的结构如下（这里照录英文，实际写作时用中文完全一样）：

```
/ui-ux-pro-max
Build a premium personal portfolio website for a frontend developer. It should look expensive,
modern, and technically impressive, with elegant animations that load well on any device.
Use the design references from the reference folder: 1.png is the hero section, 2.png is the
section right below the hero showing a work in a video + title/description format, 6.png is
the footer / bottom of the site, 7.png is the portfolio page with the full list of works,
11.png is an example of an individual project page when opening any work from the portfolio,
and 12.png is the loading screen. In the hero section, place me in the center using me.png.
For all work/project image placeholders, use example.png.

Ask me any clarifying questions you need before building.
```

三个设计要点：开头加 `/ui-ux-pro-max` 激活技能；**逐个说明每张参考图对应哪个区域**，而不是笼统说「照这个做」；最后一行 `Ask me any clarifying questions you need before building`（构建前先问我需要澄清的问题）是**关键**——AI 会停下来问 4～6 个关于风格、字体、章节、动画级别的问题，你的回答会成为整个网站的基础。回答越具体，后面的来回沟通越少。

**第四步，把动画概念讲清楚，而不是自己写代码。** 思路是：一张普通照片放在黑暗的首屏正中央很无聊，用户移动鼠标时必须有点什么发生。于是设计了「手电筒」效果，并这样描述给 AI：

> 在首屏区域，我想要一个手电筒/聚光灯光标效果。深色背景。默认情况下我的照片几乎看不见。当光标在区域上移动时，它充当聚光灯——通过一个跟随光标的柔边圆形遮罩，显示下方更亮、暖色调的照片版本。半径 100-150px，柔和的羽化边缘。实现这个效果。

这段好在哪：**效果、层次、半径、边缘质感全都给了具体参数**，正好对应「具体 > 模糊」那条原则。

**第五步，审查与打磨：把问题攒起来一次性发。** 流程是先自己浏览一遍，把「感觉不对」的地方记下来，**然后一次性发送**。他第一次构建后发现的问题包括：页面切换突兀、手电筒效果有延迟、部分元素溢出屏幕、字体与参考不匹配。发送格式：

```
以下是一些需要修复的问题。请处理所有问题：
1. [描述问题 1]
2. [描述问题 2]
3. [描述问题 3]
```

修完明显 bug 后，再跑一次**结构化质量检查**，让 AI 按六个维度诚实作答：字体排印（是否用了被过度使用的 AI 字体）、颜色、层次结构、动画、移动端、文案。最后一句提醒很关键：**你更了解你自己的网站，不要让它修你不同意的点**。

## 七、发布：交给 Agent 自动化

前面六章做完，你手上有一个能在本机跑起来的网站。最后一步是把它放到公网，拿到一个可分享的链接。

这一步不需要你逐条点按钮——它完全可以交给 Agent 自动化。你要做的只有两件事：**把一段提示词复制给 Agent**，然后在它引导下提供需要的凭证。

### 7.1 两种托管方式，怎么选


| 方式               | 适合什么                | 特点                                   |
| ---------------- | ------------------- | ------------------------------------ |
| GitHub Pages     | 开源仓库、个人项目、演示页       | 免费；和 GitHub 仓库天然一体，push 即构建          |
| Cloudflare Pages | 要绑自定义域名、要 CDN 加速的站点 | 免费额度大；构建 → 托管 → CDN → HTTPS 一条流水线自动化 |


纯静态页面、博客、官网这类内容型站点，两种都够用。**不想再注册平台就选 GitHub Pages；要自定义域名、想要更完整的构建与缓存配置，就选 Cloudflare Pages。**

### 7.2 怎么让 Agent 帮你部署

两种方式各有一份「部署提示词」，放在项目仓库的 prompt 里：

- GitHub Pages：[GitHub Pages 部署提示词](https://ravicc02.github.io/AI4U/prompt/github_page.md)
- Cloudflare Pages：[Cloudflare Pages 部署提示词](https://ravicc02.github.io/AI4U/prompt/cloudflare_page.md)

用法就一步——把下面这段复制给 Agent（Claude Code / Codex / NewMax 都行）：

```
帮我把当前项目部署到 GitHub Pages。
先读 https://ravicc02.github.io/AI4U/prompt/github_page.md ，
按里面的步骤来。需要我提供什么凭证，先告诉我，再开始操作。
```

要走 Cloudflare Pages，把提示词里的地址换成对应的那一份即可。Agent 读到提示词后，会带着你一步步走完注册、建库、构建、上线。

### 7.3 部署前要准备的凭证

提示词的第一步永远是「先确认凭证」——Agent 会先问你有没有下面这些，没有就带你申请：


| 需要什么                              | 用在哪              | 去哪拿                                                             |
| --------------------------------- | ---------------- | --------------------------------------------------------------- |
| GitHub 账号 + Personal Access Token | 建仓库、推送代码、开 Pages | GitHub → Settings → Developer settings → Personal access tokens |
| Cloudflare 账号 + API Token         | 建 Pages 项目、绑定域名  | Cloudflare Dashboard → My Profile → API Tokens                  |


## 八、新手最容易踩的坑

**配置类**

1. Base URL 多一个斜杠或缺一段路径 → 连接失败。
2. 客户端已经启动才去切换配置 → 不生效。顺序是**先切换、再重启终端、再启动**。
3. 改了环境变量没重新部署 → 看起来「没变化」。

**工作方法类**

4. **AI 说「完成了」但没验证。** 「信任但验证」是 AI 编程的黄金法则；涉及数据库、认证、支付的关键代码一定自己看一遍。
5. **提示词太模糊。** 「垃圾进，垃圾出」——模糊的需求必然导致不准确的结果。
6. **一次让 AI 做太多事。** 一个明确任务的成功率远高于一个会话堆五件事。
7. **上下文太长不清理。** 会话过长或 `CLAUDE.md` 超过 200 行，都会让 AI 忽略关键内容。
8. **AI 过度重构。** 你让它修一个 bug，它把整个文件重写了。明确说「只改这一处」。
9. **幻觉 API。** 让它先 `grep` 确认再动手。

**安全类**

12. **敏感信息硬编码。** AI 有把 Key 直接写进代码的倾向，**永远不要把 Key 提交到公开仓库**；注意别让 AI 读走 `.env`。
13. **CRUD 接口不检查权限。** AI 的第一优先级是「先让功能跑起来」，审查时把安全性放第一位。
14. **SQL 拼接、日志打印密码。** 要求参数化查询，禁止记录敏感字段。

**上线运维类**

15. **根目录没填对。** 子目录项目不填根目录，必然构建失败。
16. **SPA 忘了** `_redirects`**。** 首页正常、刷新子路由 404。
17. **第三方 DNS 下硬要绑根域名。** Pages 没有固定 IP，根域名基本只能靠迁移 NS 解决。
18. **域名一直 Pending 就先怀疑平台。** 顺序应是：先 `dig` 看解析 → 再看 Nameserver 状态 → 再检查记录值（是 `你的项目名.pages.dev`，不是 `pages.dev`）→ 最后才考虑重加。
